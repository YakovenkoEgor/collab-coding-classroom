# Автопроверка: инструменты

Каталог отдельных, самостоятельных проверяльщиков. Платформа их только
запускает (см. `checks/` в корне проекта) — зависимостей на Express, SQLite и
прочее тут нет, и наоборот: любой инструмент отсюда работает из командной
строки сам по себе.

Сейчас здесь один инструмент — `uml_check`.

## `uml_check` — UML-диаграммы классов против эталонов

Сравнивает один `.puml` студента с несколькими эталонами задания и выносит
вердикт `accepted` / `rejected` / `needs_review` плюс подробный отчёт.
Реализация по ТЗ «автоматическая проверка UML-диаграмм классов на соответствие
эталонам»: собственный парсер подмножества PlantUML, нормализация имён с
лемматизацией, сопоставление венгерским алгоритмом, метрики C1–C5, вердикт по
порогам из конфигурации задания.

Проверка **детерминирована**: один вход — один выход. Ни сети, ни вызовов LLM,
ни исполнения студенческого файла: он только читается как текст, `!include`
игнорируется.

### Установка

```bash
npm run setup:checker      # из корня проекта: создаёт .venv и ставит зависимости
```

То же самое руками:

```bash
cd checker
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt   # Windows
# .venv/bin/python -m pip install -r requirements.txt     # Linux/macOS
```

Платформа ищет интерпретатор в этом порядке: `UML_CHECK_PYTHON`,
`checker/.venv`, затем `python` из `PATH`.

### Командная строка

```bash
.venv/Scripts/python -m uml_check \
  --config tests/fixtures/bank/task_config.yaml \
  --student student.puml \
  --out report.json \
  --md teacher.md \
  --student-md student.md
```

Код возврата `0` означает «проверка выполнена» при любом вердикте; `2` — что
проверку выполнить не удалось (нет файла, битая конфигурация). Вердикт читается
из отчёта: «не принято» — нормальный результат, а не сбой.

### Библиотека

```python
from uml_check import check, load_config

report = check(load_config("task_config.yaml"), student_text)
report.verdict          # accepted | rejected | needs_review
report.score            # сходство с лучшим эталоном
report.data             # JSON по схеме п. 8 ТЗ
report.markdown         # отчёт преподавателю
report.student_markdown # отчёт студенту, без текста эталона
```

`check` принимает эталоны и в памяти: `check(config, text, refs=[("ref_1", "…")])`
— так их вызывает платформа, у неё эталоны лежат в базе, а не в файлах.

### Конфигурация задания

```yaml
task_id: bank-lab1
refs: [refs/ref_1.puml, refs/ref_2.puml, refs/ref_3.puml]
language: ru
synonyms:
  Клиент: [Заказчик, Покупатель]
  Счёт:   [Аккаунт]
required_classes:   [Клиент, Счёт]
required_relations: [[Клиент, Счёт]]
weights: {c1: 0.20, c2: 0.20, c3: 0.30, c4: 0.10, c5: 0.20}
thresholds: {accept: 0.85, reject: 0.55, match_min: 0.5, name_min: 0.6}
partial_credit: {relation_kind_mismatch: 0.5, relation_inversion: 0.25}
extra_classes_max: 0.30
check_visibility: false
check_types: false
```

Пропущенные поля берутся из `uml_check/config.py` (`DEFAULTS`) — там же лежат
значения, которых в ТЗ нет и которые пришлось назвать явно, чтобы в коде не
осталось безымянных чисел:

| поле | по умолчанию | зачем |
|---|---|---|
| `method_weight` | 0.3 | доля методов внутри C2 («для методов — отдельно, вес меньше») |
| `match_weights` | 0.5 / 0.3 / 0.2 | веса имени, атрибутов и окрестности в сопоставлении классов |
| `thresholds.member_min` | 0.7 | порог сопоставления атрибутов и методов |
| `thresholds.merge_min` | 0.5 | при каком сходстве содержимого подозревать слияние/расщепление |
| `thresholds.absorb_min` | 0.5 | какая доля атрибутов класса, найденная в чужом классе, считается переносом |
| `partial_credit.mult_missing` | 0.5 | кратность указана с одной стороны и не указана с другой |
| `ref_gap_min` | 0.03 | разрыв между эталонами, ниже которого вердикт считается спорным |
| `transitive_relations` | true | учитывать путь `A→B→C` вместо связи `A→C` как предупреждение |

`check_visibility` и `check_types` работают так, как написано в п. 3.4 ТЗ:
в метрики они не входят никогда, а при включении расхождения по видимости и
типам сопоставленных атрибутов попадают в `warnings` отчёта преподавателю.

### Тесты

```bash
npm run test:checker       # из корня проекта
```

То же самое руками:

```bash
.venv/Scripts/python -m pip install -r requirements-dev.txt
.venv/Scripts/python -m pytest tests -q
```

`tests/test_parser.py` — п. 10.1 ТЗ: каждая конструкция подмножества на двух и
более примерах, пять ошибочных файлов, четыре диаграммы других типов.
`tests/test_metamorphic.py` — п. 10.2: независимость от порядка записи,
эталон против себя даёт 1.0, синонимы счёт не меняют, удаление элементов
снижает счёт монотонно, каждый эталон принимается и опознаётся.

### Чем реализация отличается от ТЗ

- **Две независимые реализации метрик (п. 10.4) и калибровка по разметке двух
  преподавателей (п. 10.5)** не делались — договорённость по объёму первой
  итерации. Всё, что для калибровки нужно, платформа складывает в таблицу
  `check_runs`: отчёт целиком, хеш конфигурации, версии, и рядом — итоговая
  оценка преподавателя.
- **`networkx` не используется** и не стоит в зависимостях: расстояние
  редактирования графа считается по уже найденному назначению (как и
  предписано — «GED через назначение + венгерский»), а граф для этого строить
  не нужно. Понадобится для второй реализации метрик (п. 10.4) — тогда и
  появится.
- **Переименование класса** (слепая зона из п. 7) ТЗ предлагает лечить только
  словарём синонимов. Сопоставленная пара с совпавшим содержимым, но чужим
  именем дополнительно считается заменой узла в C5 и отдельно показывается
  преподавателю: иначе класс «Шестерёнка» в задании про банк давал бы ровно
  1.0.
- **Диаграммы последовательностей** распознаются по ключевым словам
  (`participant`, `activate`, …). Сообщение `A -> B : текст` без таких слов
  синтаксически не отличимо от ассоциации и будет разобрано как связь.
